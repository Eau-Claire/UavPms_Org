# MF01 — Inspection Mission Lifecycle

## 1. Purpose

MF01 covers the complete lifecycle of an inspection mission in the EVNSPC UAV–AI platform, from mission creation to assignment, preparation, execution, completion, cancellation, or controlled reassignment/update.

This flow consolidates the previously discussed “Create & Assign Inspection Mission” flow into one end-to-end mission lifecycle.

The system boundary is **EVNSPC**. `Region` means an EVNSPC operational/provincial/local power-company area, not generic North/Central/South regions.

## 2. Actors

- **Mission Manager / Admin**: create/manage missions, select GIS scope, assign personnel/drone, update/cancel when permitted.
- **Inspector / Assigned User**: receive notification, review mission, check in, receive drone when responsible, execute assigned mission.
- **Authorized Drone Handover Staff**: confirm drone handover.
- **System**: enforce RBAC + organizational scope, resolve GIS assets, persist snapshots, calculate readiness, notify, audit.

## 3. Core Domain Concepts

### Region
Operational area inside EVNSPC.

Recommended hierarchy:

`EVNSPC → Region → Substation / Line → Line Segment → Tower / Asset Component`

### UserRegion
Employee's organizational/home Region.

Temporary assignment to another Region must **not** change `UserRegion`.

### UserRegionScope
Regions where a Manager/Admin has management authority.

Creating/editing a mission requires:

`RBAC/permission + Region management scope`

### MissionAssignment
Assignment of one user to one specific mission.

Cross-region support is allowed through `MissionAssignment`.

Example:
- Employee home Region: Ninh Thuận
- Mission Region: Cà Mau
- Employee assigned to that mission

Result:
- `UserRegion` remains Ninh Thuận.
- User can access that assigned mission.
- User does **not** gain Cà Mau management scope.

### InspectionSchedule
Periodic/fixed plan/template.

Suggested fields:
- Id
- RegionId
- Name
- Frequency / RecurrenceRule
- PlannedTime
- IsActive
- CreatedByUserId
- CreatedAt
- optional default scope/assets

### InspectionMission
One executable mission instance.

Suggested fields:
- Id
- RegionId
- ScheduleId nullable
- MissionType = `SCHEDULED | AD_HOC`
- TriggerReason nullable
- CreatedByUserId
- PlannedStart
- PlannedEnd
- Status
- Boundary / GIS geometry
- actual start/completion timestamps where suitable

Rules:
- Scheduled: `ScheduleId != null`, `MissionType = SCHEDULED`
- Ad-hoc: `ScheduleId = null`, `MissionType = AD_HOC`
- Each recurrence creates a new mission instance.
- Mission Region remains historically fixed even if creator/assignee later transfers.

### MissionAsset
Explicit snapshot of assets selected for the mission.

Persist both:
1. mission GIS boundary/geometry for display/audit;
2. explicit selected assets in `MissionAsset`.

Do **not** re-run the polygon spatial query every time the mission opens.

### MissionCheckIn
Minimal P0:
- MissionId
- UserId
- CheckedInAt
- Status

Face recognition and GPS/geolocation check-in are **not required for P0**.

### DroneHandover
Minimal P0:
- MissionId
- DroneId
- HandedOverBy
- ReceivedBy
- ReceivedAt
- Condition
- Status
- optional ReturnedAt

This is a lightweight operational handover log, not a warehouse/custody engine.

## 4. Mission Status Lifecycle

Primary lifecycle:

`DRAFT → ASSIGNED → PREPARING → READY → IN_PROGRESS → COMPLETED`

Additional terminal/alternate state:

`CANCELLED`

| Status | Meaning |
|---|---|
| `DRAFT` | Mission exists but assignment/preparation is incomplete. |
| `ASSIGNED` | Required personnel/drone assignments are established. |
| `PREPARING` | Assigned users are preparing; check-in/handover may be pending. |
| `READY` | Readiness requirements pass. |
| `IN_PROGRESS` | Inspection has started. |
| `COMPLETED` | Mission execution is finished. |
| `CANCELLED` | Mission cancelled according to authorization/business rules. |

Backend owns state-transition validation.

# 5. MF01 Main Flow

## Step 1 — Mission Creation

### Input
- authenticated user
- mission title/name
- RegionId
- MissionType
- PlannedStart / PlannedEnd
- optional ScheduleId
- optional TriggerReason
- notes/description

### Output
- new InspectionMission
- status `DRAFT`
- audit event `MISSION_CREATED`

### Validate
- authenticated active user
- mission-create permission
- Region exists and active
- caller has Region management scope, unless global EVNSPC mission-management authority
- PlannedStart < PlannedEnd
- valid schedule when scheduled
- schedule Region matches mission Region
- ad-hoc mission may have null ScheduleId

### Business Rule
- Mission Region is independent from creator home Region.
- Manager creates only inside authorized UserRegionScope.
- Global EVNSPC permission may cover all Regions.
- Historical mission Region does not auto-change later.
- Mission begins in `DRAFT`.

### Exception
- unauthorized → 403
- Region not found → 404
- Region outside management scope → 403
- invalid dates → 400
- invalid/mismatched schedule → 400/409
- DB failure → rollback + 5xx

## Step 2 — Mission Scope Selection on GIS

### Input
One or more of:
- grid/cell
- drag-selected area
- polygon
- direct line/tower/assets

### Output
- authorized candidate assets
- confirmed mission boundary/geometry
- explicit MissionAsset records

### Validate
- valid GIS geometry
- selected assets exist/active
- assets belong to mission Region
- assets are within caller management scope
- final list non-empty
- duplicates rejected/deduplicated

### Business Rule
- Backend performs spatial authorization/filtering.
- If polygon overlaps in-scope and out-of-scope assets, Backend returns only in-scope assets.
- User confirms final candidate list.
- Persist boundary + explicit MissionAsset snapshot.
- Do not recompute mission membership from polygon on every read.

### Exception
- malformed polygon → 400
- no assets → validation error
- out-of-scope direct asset submission → 403
- stale/deleted asset → 404/409
- spatial DB failure → 5xx

## Step 3 — Assign Personnel + Drone

### Input
- MissionId
- personnel assignment list
- generic AssignmentRole
- drone
- responsible receiver where applicable

### Output
- MissionAssignment records
- drone reservation/assignment
- mission may transition `DRAFT → ASSIGNED`
- audit records

### Validate
- mission exists
- state permits assignment
- assignee exists/active
- no duplicate active assignment
- drone exists and is operational/available
- caller authorized

### Business Rule
- Cross-region personnel assignment is allowed.
- Cross-region assignment does not modify UserRegion.
- Cross-region assignment does not grant UserRegionScope.
- Use generic AssignmentRole, not speculative hardcoded roles.
- Assigned mission access derives from MissionAssignment.
- Move to ASSIGNED when required assignments are complete.

### Exception
- duplicate assignment → 409
- unavailable/inactive user → 409
- unavailable/damaged drone → 409
- invalid state → 409
- unauthorized → 403

## Step 4 — Notify Assigned Users

### Input
Committed assignment/schedule/scope/reassignment/cancellation changes.

### Output
Notification/event for affected users.

### Business Rule
- Notify after successful persistence.
- Reassigned replacement receives new notification.
- Removed/replaced user receives relevant change notice.
- Notification failure should be logged/retried rather than corrupting mission state unless project policy says otherwise.

## Step 5 — Assigned Users Review Mission

Assigned user may view:
- mission Region
- GIS boundary
- selected MissionAssets
- schedule
- team
- AssignmentRole
- drone
- current status

### Authorization
Access if:
- management permission + Region scope; or
- active MissionAssignment; or
- explicit global/admin permission.

### Business Rule
- Inspector GIS access is mission-scoped.
- Inspector sees only MissionAssets of the assigned mission.
- Mission assignment does not grant general Region management authority.

## Step 6 — Drone Handover & Condition Confirmation

### Input
- mission
- drone
- handover staff
- receiving assigned user
- condition
- optional checklist

### Output
- DroneHandover record
- drone marked received for mission
- preparation/readiness recalculated

### Validate
- mission permits handover
- drone matches assigned drone
- receiver is authorized/assigned
- handover staff authorized
- condition recorded
- duplicate active handover prevented

### Business Rule
- Keep P0 lightweight.
- Log who handed over, who received, drone, mission, time, condition, status.
- Failed condition blocks READY.
- Replacement drone uses controlled alternate flow.

## Step 7 — Team Check-in / Attendance Confirmation

### Input
MissionId + authenticated assigned user.

### Output
MissionCheckIn with server-side CheckedInAt.

### Validate
- user assigned to mission
- state permits check-in
- no duplicate
- active account

### Business Rule
- No face recognition required P0.
- No GPS/geolocation required P0.
- Server is source of truth for CheckedInAt.
- Required assignees must check in before READY.

## Step 8 — Mission Ready

Backend evaluates readiness.

Minimum conditions:
- required MissionAssignments exist
- required users checked in
- required drone assigned
- drone handover completed
- drone condition accepted
- MissionAssets non-empty
- mission not cancelled

Transition:

`ASSIGNED/PREPARING → READY`

Frontend must not force READY directly.

## Step 9 — Start Inspection Mission

### Input
MissionId + authorized assigned user/leader according to project policy.

### Output
- status `IN_PROGRESS`
- actual start time
- audit event

### Validate
- current status is READY
- caller authorized
- mission not cancelled
- no concurrent duplicate start

### Business Rule
`READY → IN_PROGRESS` is controlled by Backend.

This action manages mission state. It does not imply autonomous UAV flight-control.

## Step 10 — Execute Inspection

Mission remains `IN_PROGRESS`.

Inspection media, flight logs, AI detections, etc. link to MissionId but belong to their own modules/flows.

Normal assignment/scope/schedule mutations after IN_PROGRESS are restricted. Exceptional changes require explicit authorization + audit.

## Step 11 — Complete / Cancel / Reassign / Update

### Complete
`IN_PROGRESS → COMPLETED`

Record actual completion time and audit.

### Cancel
Normally:

`DRAFT | ASSIGNED | PREPARING | READY → CANCELLED`

Cancellation after IN_PROGRESS should be separately defined and not casually allowed.

### Employee unavailable
1. employee reports unavailable / Manager marks unavailable
2. current assignment updated/revoked
3. Manager assigns replacement
4. replacement notified
5. readiness recalculated
6. audit

### Drone unavailable/damaged
1. close/invalidate current assignment/handover as needed
2. assign replacement
3. repeat handover + condition confirmation
4. readiness recalculated
5. audit

### Scope/schedule update
Allowed only in valid pre-execution states. Notify affected users and audit material changes.

# 6. Core Authorization Rules

## Mission Create/Edit
`Permission/RBAC + UserRegionScope`

Example:
A Manager with Ninh Thuận scope may create/edit Ninh Thuận missions, but not Cà Mau unless given Cà Mau scope or global EVNSPC authority.

## Assigned Mission Access
`MissionAssignment`

This enables cross-region operational work without granting Region management power.

## Backend Enforcement
Never rely on:
- hidden frontend buttons
- frontend Region filters
- submitted RegionId
- submitted asset IDs
- client-submitted status

Backend validates permission, scope, assignment, state, and asset scope.

# 7. Audit Requirements

Audit at least:
- mission created
- Region/scope selected or changed
- MissionAsset changes
- personnel assignment/reassignment/removal
- drone assignment/replacement
- drone handover/condition
- check-in
- status transitions
- schedule changes
- cancellation
- exceptional IN_PROGRESS changes

# 8. Transaction / Concurrency Rules

Use transactions for:
- mission creation with dependent rows
- MissionAsset snapshot replacement
- assignment/reassignment + readiness recalculation
- drone replacement + readiness recalculation
- check-in + readiness recalculation

Use optimistic concurrency/versioning where suitable.

Prevent:
- duplicate assignment
- duplicate start
- stale overwrite
- READY computed from stale data

# 9. Minimum API Shape

Exact routes should follow the current codebase conventions.

```text

```

# 10. Acceptance Scenarios

1. Manager creates mission inside authorized Region scope → success.
2. Manager creates mission outside scope → 403.
3. Polygon crosses scope boundary → only authorized assets returned/selectable.
4. Cross-region Inspector assignment → succeeds without changing UserRegion/UserRegionScope.
5. Scheduled mission → ScheduleId non-null, MissionType SCHEDULED, Region matches schedule.
6. Ad-hoc mission → ScheduleId null, MissionType AD_HOC, optional TriggerReason.
7. Drone condition failed → mission cannot become READY.
8. Required member unavailable → replacement flow + notification + readiness recalculation.
9. Start before READY → 409.
10. READY mission starts → IN_PROGRESS + actual start time + audit.

# 11. Out of P0 / Do Not Overbuild

Do not make these required for MF01 P0:
- face-recognition check-in
- GPS/geofenced employee check-in
- autonomous drone flight-control
- complex warehouse inventory/custody engine
- speculative team roles not confirmed by requirements

# 12. Final MF01 Summary

1. Mission Creation

3. Assign Personnel + Drone
4. Notify Assigned Users
5. Assigned Users Review Mission
6. Drone Handover & Condition Confirmation
7. Team Check-in / Attendance Confirmation
8. Mission Ready
9. Start Inspection Mission
10. Execute Inspection
11. Complete / Cancel / Reassign / Update

Primary lifecycle:

`DRAFT → ASSIGNED → PREPARING → READY → IN_PROGRESS → COMPLETED`

Alternate terminal state:

`CANCELLED`

Critical separation:

- `UserRegion` = employee home/organizational area
- `UserRegionScope` = where a Manager may manage missions
- `MissionAssignment` = which specific mission a user is assigned to
