## 2. Architecture Review / Decision

### 2.1. MF02 không chọn scope từ đầu lần thứ hai

MF01 đã có Proposed Scope Snapshot.

Do đó MF02 bắt đầu từ:

> **Open READY Pre-Mission Assessment → Review/Confirm Scope → Select Final Resources → Enter/Confirm Mission Information → Revalidate → Commit Mission**

Không bắt Manager lặp lại Region → Line → Tower từ zero.

### 2.2. Khi nào phải quay lại MF01

Re-assessment bắt buộc nếu MF02 thay đổi material input:

- Region / Line / core inspection scope;
- planned window đáng kể;
- operation site/geometry;
- policy-sensitive condition.

Thay candidate Inspector/UAV trong danh sách MF01 có thể không cần full site re-assessment nhưng phải revalidate eligibility/current availability.

### 2.3. Assignment semantics

MF02 mới là nơi:

- chọn personnel chính thức;
- assign UAV chính thức;
- tạo reservation/booking;
- tạo `InspectionMission`;
- tạo `MissionAssets`;
- gửi notification.

MF01 chỉ cung cấp candidate readiness snapshot.

## 3. Main Flow Specification

| Đặc tả | Chi tiết |
|---|---|
| **Main Flow** | **MF02 — Create & Assign Inspection Mission** |
| **Priority** | **P0 — Core Business Flow** |
| **Description** | Mission Manager sử dụng một `PreMissionAssessment` ở trạng thái `READY` để tạo mission. Hệ thống load proposed scope/time và eligible resources đã được MF01 đánh giá. Manager review/confirm scope, chọn Inspector/Pilot và UAV cuối cùng, nhập/confirm mission metadata. Backend revalidate assessment freshness, management scope, personnel/drone availability, technical inspection validity và conflict. | **Actors** | Mission Manager; Inspector/Pilot; UAV-PMS Backend; Notification Worker. |
| **Input** | assessmentId; mission metadata; confirmed scope; selected inspectorIds/roles; selected droneIds; schedule; optional notes/priority/missionType. |
| **Output** | InspectionMission; MissionAssets snapshot; MissionAssignments; MissionDrones; resource bookings; audit logs; outbox/notifications; assignment response status. |

## 5. Mission / Assignment State Model

### 5.1. Mission status

Recommended:

```text
DRAFT
  ↓
PENDING_ACCEPTANCE
  ├── ASSIGNED / ACCEPTED
  ├── POSTPONED
  └── CANCELLED

ASSIGNED / ACCEPTED
  ↓
# MF03 handles field check-in / execution
```

Do not use `READY_FOR_EXECUTION` in MF02. Field readiness belongs MF03.

### 5.2. MissionAssignment status

```text
PENDING
  ├── ACCEPTED
  ├── POSTPONED
  ├── REPLACED
  └── CANCELLED
```

For multiple assigned personnel:

- each assignment has independent status;
- use `IsRequired`;
- mission becomes accepted only when **all required assignments** satisfy acceptance policy;
- at least one required `LEAD_INSPECTOR` / `PILOT` must exist if project policy requires it.

### 5.3. MissionDrone status

```text
RESERVED → ASSIGNED → HANDED_OVER → IN_USE → RETURNED
          └────────→ RELEASED / CANCELLED
```

MF02 normally ends at `RESERVED/ASSIGNED`.

## 6. Validation

- **V01 Authentication:** user authenticated.
- **V02 Create Permission:** user has mission management permission.
- **V03 Assessment Exists:** `assessmentId` exists.
- **V04 Assessment Status:** assessment must be `READY`.
- **V05 Assessment Not Expired:** `ValidUntil > now`.
- **V06 Assessment Not Consumed:** assessment cannot be consumed by another mission.
- **V07 Management Scope:** confirmed assets remain inside current authorized scope.
- **V08 Scope Consistency:** confirmed mission scope must match assessment snapshot unless re-assessed.
- **V09 Required Fields:** missionName, plannedStartAt, plannedEndAt, at least one MissionAsset.
- **V10 Time Validation:** end > start.
- **V11 Personnel Candidate:** selected user was eligible or passes current revalidation.
- **V12 Personnel Role:** assignment role valid.
- **V13 Personnel Availability:** no overlapping active booking.
- **V14 Drone Candidate:** selected drone was eligible or passes current revalidation.
- **V15 Drone Operational Status:** must be `AVAILABLE` at commit time.
- **V16 Technical Inspection Validity:** latest required technical inspection not expired.
- **V17 Technical Health:** health passes mission policy.
- **V18 Drone Schedule Conflict:** no overlapping active booking.
- **V19 Duplicate Asset:** unique per mission.
- **V20 Duplicate Assignment:** unique `(MissionId, UserId, AssignmentRole)` or chosen normalized rule.
- **V21 Duplicate Drone:** unique `(MissionId, DroneId)`.
- **V22 Mission State:** scope/assignment edits only in allowed states.
- **V23 Inspector Response Authorization:** only assigned user may accept/postpone own assignment.
- **V24 Postpone Reason:** required and nonblank.
- **V25 Concurrency:** stale mission/assessment update rejected.
- **V26 Idempotency:** duplicate create request with same key returns same result, not a second mission.

## 7. Business Rules

- **BR01 MF01 Dependency:** standard mission creation requires a READY, unexpired assessment.
- **BR02 Assessment Consume Once:** one assessment may create at most one mission unless explicit clone workflow exists.
- **BR03 Scope Snapshot:** `MissionAssets` copied from confirmed assessment scope and remains historical snapshot.
- **BR04 No Silent Scope Expansion:** MF02 cannot silently add out-of-assessment assets.
- **BR05 Resource Revalidation:** MF01 readiness is snapshot; availability must be rechecked before commit.
- **BR06 Technical Revalidation, Not Reinspection:** MF02 checks inspection validity/current drone state; it does not rerun Betaflight/FC inspection.
- **BR07 Reservation at Commit:** UAV/personnel become booked only inside mission creation transaction.
- **BR08 No Partial Mission:** Mission + scope + required assignments + drone allocation must commit atomically.
- **BR09 Notification Is Async Side Effect:** notification failure must not rollback an already committed valid mission.
- **BR10 Transactional Outbox:** notification/domain event is written in same transaction as mission.
- **BR11 Inspector Access:** Inspector can access only assigned mission and its MissionAssets.
- **BR12 Accept/Postpone Only:** normal Inspector response is Accept or Postpone, no direct Reject.
- **BR13 Postpone Requires Reason:** Postpone records reason, user, timestamp.
- **BR14 Manager Adjustments:** schedule/resource/scope changes follow state rules and may trigger MF01 re-assessment.
- **BR15 Multiple Required Assignments:** mission cannot be considered fully accepted while required assignment remains pending/postponed.
- **BR16 Backend State Authority:** frontend does not directly set mission/assignment state.
- **BR17 Audit:** create/update/assignment/accept/postpone/cancel must audit.
- **BR18 Optimistic Concurrency:** mission and assessment must use version token.
- **BR19 No Physical Check-in Here:** field check-in belongs MF03.
- **BR20 No Post-flight Here:** upload/Cloud AI belongs MF04.

# 9. Database Impact Review

## 9.1. Existing tables reused

Keep and harden:

- `InspectionMissions`
- `MissionAssets`
- `MissionAssignments`
- `MissionDrones`
- `Drones`
- `Users`
- `Notifications`
- `AuditLogs`

MF02 does **not** require another mission-like table if MF01 has `PreMissionAssessments`.

## 9.2. Change `InspectionMissions`

Add:

```text
PreMissionAssessmentId UUID NULL FK PreMissionAssessments
AcceptedAt timestamptz NULL
PostponedAt timestamptz NULL
PostponeReason text NULL
Version bigint NOT NULL DEFAULT 1
CreatedAt timestamptz NOT NULL
UpdatedAt timestamptz NOT NULL
```

Recommended migration strategy:

1. add nullable FK first for legacy data;
2. v2 application requires it for normal mission creation;
3. after legacy migration, optionally enforce NOT NULL for v2 missions via version/type rule.

Constraint:

```text
CHECK (PlannedEnd > PlannedStart)
```

Unique:

```text
UNIQUE (PreMissionAssessmentId)
WHERE PreMissionAssessmentId IS NOT NULL
```

This enforces single-consume at DB level.

## 9.3. Harden `MissionAssets`

Required:

```text
UNIQUE (MissionId, AssetId)
```

Use real FK to canonical Asset entity.

Do not use soft duplicate suppression only in application code.

## 9.4. Harden `MissionAssignments`

Recommended fields:

```text
AssignmentRole varchar NOT NULL
Status varchar NOT NULL
IsRequired boolean NOT NULL DEFAULT true
AssignedAt timestamptz NOT NULL
RespondedAt timestamptz NULL
ResponseReason text NULL
Version bigint NOT NULL DEFAULT 1
```

Constraint examples:

```text
CHECK (Status IN ('PENDING','ACCEPTED','POSTPONED','REPLACED','CANCELLED'))
CHECK (
  Status <> 'POSTPONED'
  OR (ResponseReason IS NOT NULL AND length(trim(ResponseReason)) > 0)
)
```

Unique policy depends on whether one user can hold multiple roles:

```text
UNIQUE (MissionId, UserId, AssignmentRole)
```

or, if exactly one role/user/mission:

```text
UNIQUE (MissionId, UserId)
```

Choose one and enforce consistently.

## 9.5. Harden `MissionDrones`

Recommended fields:

```text
Status varchar NOT NULL
ReservedAt timestamptz NULL
ReleasedAt timestamptz NULL
Version bigint NOT NULL DEFAULT 1
```

Constraint:

```text
UNIQUE (MissionId, DroneId)
```

## 9.6. Resource booking conflict prevention

Current `MissionAssignments` / `MissionDrones` reference mission schedule indirectly, so DB cannot easily apply overlap exclusion across joined `InspectionMissions`.

**Recommended v2 hardening:** add `ResourceBookings`.

```text
Id UUID PK
MissionId UUID FK InspectionMissions
UserId UUID NULL FK Users
DroneId UUID NULL FK Drones
StartAt timestamptz NOT NULL
EndAt timestamptz NOT NULL
Status varchar NOT NULL
CreatedAt timestamptz NOT NULL
```

Constraint:

```text
CHECK ((UserId IS NOT NULL) <> (DroneId IS NOT NULL))
CHECK (EndAt > StartAt)
```

With PostgreSQL `btree_gist`, add separate partial exclusion constraints to reject overlapping active bookings for same user/drone.

If this is too heavy for current sprint, minimum safe implementation:

- lock selected resource rows (`SELECT ... FOR UPDATE`);
- re-query overlapping missions in the same transaction;
- create assignment/allocation only after conflict check;
- still plan `ResourceBookings` as hardening migration.

## 9.7. Transactional Outbox

Add if not already present:

```text
OutboxMessages
- Id UUID PK
- Type
- Payload jsonb
- OccurredAt
- ProcessedAt NULL
- RetryCount
- LastError NULL
```

Create outbox event in the same transaction as mission creation.

Notification worker later consumes it.

This eliminates the bad pattern:

```text
DB commit mission
→ call push notification inline
→ push fails
→ controller returns 500 although mission already exists
```

# 10. Atomic Transaction Boundary

Mission creation transaction:

```text
BEGIN

1. Lock/load READY assessment
2. Verify not expired/not consumed
3. Revalidate management scope
4. Lock selected Users/Drones
5. Revalidate resource conflicts
6. Revalidate drone technical inspection validity
7. INSERT InspectionMission
8. INSERT MissionAssets
9. INSERT MissionAssignments
10. INSERT MissionDrones
11. INSERT ResourceBookings
12. Mark assessment CONSUMED + ConsumedMissionId
13. INSERT AuditLog
14. INSERT OutboxMessage

COMMIT
```

On any required step failure:

```text
ROLLBACK
```

No partially created mission.

# 11. API Contract v2

Suggested endpoints:

```http
POST /api/v2/missions
GET  /api/v2/missions/{missionId}
PATCH /api/v2/missions/{missionId}

POST /api/v2/missions/{missionId}/assignments/{assignmentId}/accept
POST /api/v2/missions/{missionId}/assignments/{assignmentId}/postpone

GET /api/v2/pre-mission-assessments/{assessmentId}/create-mission-context
```

Create request:

```json
{
  "assessmentId": "uuid",
  "missionName": "Inspection Line ...",
  "description": "...",
  "plannedStartAt": "ISO-8601",
  "plannedEndAt": "ISO-8601",
  "priority": "NORMAL",
  "assignments": [
    {
      "userId": "uuid",
      "role": "LEAD_INSPECTOR",
      "isRequired": true
    }
  ],
  "droneIds": ["uuid"]
}
```

Important:

- `assetIds` normally come from assessment snapshot;
- if API accepts modified `assetIds`, backend compares them with assessment and may return `REASSESSMENT_REQUIRED`;
- support `Idempotency-Key`;
- API does not trust frontend-provided `READY`/`AVAILABLE` flags.

# 12. Clean Code / Refactor Guidance

Recommended application services:

```text
CreateInspectionMissionCommandHandler
MissionCreationPolicy
AssessmentConsumptionPolicy
ResourceConflictService
MissionScopeSnapshotService
MissionAssignmentService
MissionAcceptancePolicy
MissionPostponePolicy
OutboxPublisher
AuditService
```

Do not:

- put EF queries + role logic + notification calls directly in controller;
- let frontend choose arbitrary status;
- duplicate MF01 technical logic inside MF02;
- use “check then insert” without transaction/locking;
- catch every exception and return HTTP 500;
- store candidate arrays as opaque JSON if they are used for relational constraints.

Use:

- domain-specific error codes;
- cancellation tokens;
- transaction boundary in application layer;
- structured logs with `assessmentId`, `missionId`, `userId`;
- optimistic concurrency;
- integration tests against PostgreSQL for unique/exclusion constraints.

# 13. Test Checklist

Minimum:

- cannot create from NOT_READY assessment.
- cannot create from EXPIRED assessment.
- same assessment cannot create two missions.
- out-of-scope assets rejected.
- scope material change requires re-assessment.
- concurrent requests with same idempotency key create one mission.
- concurrent requests trying same UAV/time produce one winner.
- concurrent requests trying same required personnel/time produce one winner.
- expired technical inspection prevents commit.
- mission + assets + assignments + drones roll back together on failure.
- notification failure does not delete/rollback committed mission.
- Inspector can accept only own assignment.
- Postpone requires reason.
- multiple required assignments obey acceptance policy.
- Inspector cannot Reject in normal flow.
- field check-in is not triggered by MF02.

# 14. Definition of Done

MF02 v2.0 is done when:

1. Mission creation consumes a READY MF01 assessment.
2. Scope is reviewed, not rebuilt redundantly.
3. Resource state is revalidated at commit.
4. Mission creation is atomic.
5. Scope is saved as MissionAssets snapshot.
6. Required personnel/UAV cannot be double-booked under concurrent requests.
7. Accept/Postpone is assignment-aware and auditable.
8. Notification uses transactional outbox or equivalent reliable async delivery.
9. Backend owns authorization/state transitions.
10. MF02 cleanly hands off to MF03 without performing field check-in or flight execution.
