# Codex Context: Inspection Mission Management (Backend)

## 1. Purpose

Implement the backend business flow for creating, scoping, assigning, viewing, and managing UAV electrical-infrastructure inspection missions.

This document is the implementation context for Codex. Treat the rules below as the intended business behavior unless the existing codebase has an explicitly conflicting domain rule that must be preserved.

## 2. Core Domain Flow

```text
Mission Manager
  -> Create Mission
  -> Select inspection scope on GIS
       -> select Region/Substation/Line/Tower, OR
       -> draw a polygon, OR
       -> manually select towers
  -> Backend resolves candidate towers
  -> Manager confirms final tower list
  -> Backend stores Mission + MissionAssets
  -> Manager assigns Inspector(s)
  -> Backend stores MissionAssignments
  -> Assigned Inspector can access the mission
  -> Mission-scoped GIS returns only MissionAssets available to that inspector
  -> Inspector performs inspection
  -> Mission status/progress is updated
```

Important: the GIS polygon is a selection tool. The final confirmed asset/tower list must be persisted as the mission scope. Do not recalculate the mission's historical scope from the polygon every time the mission is opened.

---

## 3. Authorization Model

There are two different authorization dimensions. Do not implement this as RBAC alone.

### 3.1 Role/Permission Authorization

Answers: **What may this user do?**

- Only a user with mission-management permission may create/manage a mission.
- Suggested roles: `ADMIN`, `MISSION_MANAGER`, or `OPERATION_MANAGER`.
- `INSPECTOR` does not create missions unless the business rules are changed later.

Prefer permission-based checks in code over hard-coding role names everywhere if the existing system already has RBAC/permission abstractions.

### 3.2 Management Scope Authorization

Answers: **Where may this manager do it?**

A Mission Manager may create/manage missions only inside the geographical/asset scope assigned to that manager.

Example:

```text
Manager A
└── Region A
    ├── Substation A1
    │   ├── Line L01
    │   │   ├── Tower T01
    │   │   ├── Tower T02
    │   │   └── Tower T03
    │   └── Line L02
    └── Substation A2
```

Manager A must not create a mission containing an asset from Region B, even if the client manually sends the ID.

Backend must enforce this rule. Frontend filtering is not authorization.

### 3.3 Inspector Mission Authorization

Answers: **Which operational data may this inspector access?**

- An Inspector may access only missions assigned to that Inspector.
- In a mission-scoped GIS view, the Inspector may access only assets/towers belonging to that mission's persisted `MissionAssets` scope.
- Directly requesting another mission or an asset outside the assigned mission scope must be rejected.

Admin/Manager GIS visibility may be broader according to their management scope and permissions.

---

## 4. Asset Hierarchy

Use the electrical infrastructure hierarchy:

```text
Region
  -> Substation
      -> Line
          -> Tower
```

A mission may be scoped through higher-level assets, but the final inspection targets should resolve to explicit inspectable assets/towers where applicable.

## 5. Mission Input

### Mission information

Expected fields, adapted to the existing domain model:

- `missionName`
- `description`
- `plannedStartTime`
- `plannedEndTime`
- `priority` (if supported)
- optional hierarchy context such as `regionId`, `substationId`, `lineId`

### GIS inspection area

The client may provide:

- a polygon/geometry drawn on GIS;
- selected Region/Substation/Line;
- explicit tower IDs;
- manual selection/deselection after spatial preview.

Use GeoJSON or the geometry format already used by the project. Do not introduce a second GIS representation without need.

### Assignment

- `inspectorIds[]`
- optional `droneId` only if UAV assignment already exists/is required by the domain

## 6. GIS Selection Flow

### Polygon selection

Recommended interaction:

```text
Frontend draws polygon
  -> sends geometry to Backend spatial-preview endpoint
  -> Backend validates geometry
  -> Backend intersects polygon with creator's authorized management scope
  -> PostGIS query finds candidate towers
  -> Backend returns ONLY authorized candidate towers
  -> Frontend highlights candidates
  -> Manager manually adds/removes towers if allowed
  -> Manager confirms final tower IDs
  -> Backend validates the IDs again
  -> Mission scope is persisted
```

The spatial-preview endpoint must not create a mission or mutate mission scope.

### Manual selection

Managers may also select individual towers or select a Line/Substation and let Backend resolve its towers. Every resolved asset must still pass management-scope authorization.

### Polygon crossing authorization boundaries

If a polygon covers both authorized and unauthorized regions/assets:

- do not return unauthorized assets;
- do not make them selectable;
- return only candidate assets inside the creator's management scope.

If the final create/update request nevertheless contains an unauthorized asset ID, reject the operation.

## 7. Output

A successful mission operation should expose, as appropriate:

### Mission record

- `missionId`
- mission metadata
- planned schedule
- status/progress

### Mission scope

- stored GIS geometry/polygon if required for display/audit
- confirmed `MissionAssets`
- hierarchy information required by the client

### Assignment

- assigned inspectors
- assignment status/details if modeled

### GIS access scope

For an Inspector, mission-scoped endpoints return only assets authorized through the mission assignment and `MissionAssets` relation.

## 8. Validation Rules

Implement validation at the Backend boundary/domain layer as appropriate.

1. **Authentication**: protected mission operations require an authenticated user.
2. **Create permission**: creator must have mission-management permission.
3. **Management scope**: every selected/resolved asset must be inside the creator's assigned scope.
4. **Required mission data**: mission must contain required metadata and at least one inspection target before it can be assigned/activated.
5. **Schedule**: `plannedEndTime > plannedStartTime`.
6. **Inspector existence**: every assigned inspector must exist.
7. **Inspector eligibility**: assigned user must have the required Inspector role/permission.
8. **Asset existence**: selected Region/Substation/Line/Tower must exist.
9. **Asset hierarchy**: selected assets must have valid hierarchy relationships.
10. **GIS geometry**: polygon must be valid and use the coordinate system expected by PostGIS/project GIS conventions.
11. **Spatial selection**: polygon-derived candidates must satisfy the spatial predicate chosen by the application and must be inside management scope.
12. **Duplicate assets**: the same asset must not appear more than once in one mission.
13. **Duplicate assignment**: the same inspector must not be assigned twice to one mission.
14. **Mission state**: scope/assignment changes are allowed only in appropriate mission states.
15. **Server-side revalidation**: never trust tower IDs returned previously by spatial preview. Revalidate them during create/update.

## 9. Business Rules

### BR01 - Mission Creator
Only users with mission-management permission may create missions.

### BR02 - Creator Management Scope
A Mission Manager may create or modify a mission only for Region/Substation/Line/Tower assets inside the scope assigned to that manager.

### BR03 - Mission Assignment
A mission may be assigned to one or more eligible Inspectors.

### BR04 - Asset Hierarchy
Mission scope follows `Region -> Substation -> Line -> Tower`.

### BR05 - GIS Polygon Selection
A polygon is used to spatially query candidate towers. The query must be constrained by the creator's management scope.

### BR06 - Explicit Confirmation
Spatial-query results are candidates only. The manager confirms the final asset list before it becomes mission scope.

### BR07 - Manual Asset Selection
Managers may manually select/deselect towers and may select higher-level hierarchy objects where supported. Backend resolves and validates the resulting tower/assets list.

### BR08 - Mission Scope Snapshot
Persist the final mission-to-asset relationship, e.g. `MissionAssets`. Do not rely only on the polygon for later authorization/history.

### BR09 - Assigned Mission Visibility
An Inspector may access only missions assigned to that Inspector.

### BR10 - Mission GIS Visibility
When an Inspector opens GIS in the context of an assigned mission, Backend returns only the assets in that mission's `MissionAssets` scope.

### BR11 - General GIS Visibility
Admin/Manager may have broader GIS visibility according to permissions and management scope. Mission-scoped Inspector visibility must remain restricted.

### BR12 - Mission Lifecycle
Suggested lifecycle if compatible with the existing domain:

```text
DRAFT -> ASSIGNED -> IN_PROGRESS -> COMPLETED
   \                         
    -> CANCELLED
```

Do not replace existing mission statuses blindly. Map these semantics to the current enum/state machine if one already exists.

### BR13 - Edit Restrictions
- `DRAFT`: scope and assignment may be edited.
- `ASSIGNED`: scope/assignment may be edited if business permits, with audit.
- `IN_PROGRESS`: scope changes should be restricted; any permitted change must be audited.
- `COMPLETED` / `CANCELLED`: scope should be immutable.

### BR14 - Auditability
Audit at least:

- mission creation;
- mission scope changes;
- inspector assignment/unassignment;
- significant mission status transitions.

## 10. Exceptions / Expected Backend Behavior

| Code | Condition | Expected behavior |
|---|---|---|
| EX01 | Unauthenticated | `401 Unauthorized` |
| EX02 | User lacks mission-management permission | `403 Forbidden` |
| EX03 | Selected asset is outside creator management scope | `403 Forbidden`; do not partially create/update the mission |
| EX04 | Inspector does not exist | Reject assignment with validation/not-found response |
| EX05 | User exists but is not eligible as Inspector | Reject assignment |
| EX06 | Empty mission scope | Do not allow assignment/activation; create-as-draft only if domain permits empty drafts |
| EX07 | Invalid GIS polygon | `400 Bad Request` |
| EX08 | Valid polygon contains no authorized towers | Return an empty candidate list; no mutation |
| EX09 | Polygon crosses management boundaries | Return only authorized candidates |
| EX10 | Duplicate asset | Reject or normalize without duplicate relation; prefer explicit validation consistent with project conventions |
| EX11 | Duplicate inspector assignment | Do not create duplicate assignment |
| EX12 | Invalid mission state for requested mutation | Reject with domain/conflict response |
| EX13 | Mission requested by unassigned Inspector | `403 Forbidden` (or project-standard authorization response) |
| EX14 | Inspector requests asset outside assigned MissionAssets | `403 Forbidden` / do not expose the asset through mission-scoped endpoint |
| EX15 | Concurrent mission update | Use the project's concurrency/version strategy; prevent silent overwrite |
| EX16 | Spatial query failure | Fail safely; do not persist an incomplete mission scope |
| EX17 | Database failure during create/update | Keep operation atomic; rollback related Mission/MissionAssets/MissionAssignments writes |

Use the project's existing error/result conventions instead of inventing a parallel response envelope.

- unique `(missionId, inspectorId)`
- proper FKs
- spatial index for tower coordinates and mission geometry where useful

Names are examples. Follow the project's current routing/CQRS conventions.

```text
POST  /api/missions/spatial-preview
POST  /api/missions
PUT   /api/missions/{missionId}
PUT   /api/missions/{missionId}/assets
POST  /api/missions/{missionId}/assignments

GET   /api/missions/{missionId}
GET   /api/missions/{missionId}/assets
GET   /api/missions/{missionId}/gis
PATCH /api/missions/{missionId}/status
```

### `POST /api/missions/spatial-preview`

Purpose: query candidate towers only. No mutation.

Example input:

```json
{
  "geometry": {
    "type": "Polygon",
    "coordinates": []
  }
}
```

Backend flow:

```text
Authenticate
-> authorize mission-management permission
-> load creator management scope
-> validate geometry
-> spatial query towers
-> intersect/filter by management scope
-> return authorized candidates
```

### `POST /api/missions`

Conceptual input:

```json
{
  "name": "Inspection Line 110kV - Area A",
  "description": "...",
  "plannedStartTime": "...",
  "plannedEndTime": "...",
  "area": {
    "type": "Polygon",
    "coordinates": []
  },
  "assetIds": [
    "tower-001",
    "tower-002",
    "tower-003"
  ],
  "inspectorIds": [
    "user-123"
  ]
}
```

Backend must revalidate permissions, management scope, assets, and inspectors inside the create operation. Do not assume a prior preview makes the request trusted.

## 13. Transaction Boundary

Creating a mission with confirmed assets and initial assignments should be atomic where the current architecture permits it:

```text
Create Mission
+ Create MissionAssets
+ Create initial MissionAssignments
+ Write required audit information
= commit
```

If a required write fails, do not leave a half-created active/assigned mission.

If audit logging is asynchronous in the existing architecture, preserve that architecture rather than forcing audit persistence into the same DB transaction.

---

## 14. Security Requirements

1. Never authorize based only on data hidden/filtered by the frontend.
2. Every create/update request must validate creator management scope server-side.
3. Every Inspector mission request must validate assignment server-side.
4. Every mission-scoped asset/GIS request must validate both mission assignment and asset membership.
5. Do not expose unauthorized asset metadata through spatial preview, search, counts, or error details.
6. Prefer existing authorization policies/handlers over scattered role comparisons.

Authorization summary:

```text
MANAGER
  -> Role/Permission check
  -> Management Scope check
  -> may create/manage Mission within authorized scope

INSPECTOR
  -> Role/Permission check
  -> Mission Assignment check
  -> may access assigned Mission
  -> may access only MissionAssets in mission-scoped GIS
```

## 15. Implementation Guidance for Codex

Before changing code:

1. Inspect the existing Mission, Asset, User/RBAC, GIS, authorization, and audit implementations.
2. Reuse current entities, repositories, CQRS/MediatR handlers, result types, middleware, policies, and naming conventions.
3. Identify how manager geographical scope is currently represented. If it does not exist, implement the smallest coherent model needed rather than inventing several overlapping scope tables.
4. Check whether PostgreSQL already has PostGIS enabled and whether spatial types are already used before adding GIS dependencies/migrations.
5. Do not remove or rename existing public APIs without a demonstrated need.
6. Do not implement authorization only in controllers. Keep domain/application authorization reusable for all entry points.
7. Add tests for authorization boundaries, especially forged asset IDs and forged mission IDs.

### Minimum test scenarios

- authorized manager creates mission entirely inside own scope;
- manager cannot create mission with one out-of-scope tower mixed into otherwise valid towers;
- polygon preview never leaks out-of-scope towers;
- invalid polygon is rejected;
- manager can assign an eligible inspector;
- invalid/non-inspector assignment is rejected;
- duplicate asset/assignment is prevented;
- assigned inspector can read assigned mission;
- unassigned inspector cannot read mission;
- assigned inspector receives only MissionAssets through mission GIS;
- inspector cannot fetch an out-of-scope tower by modifying the request;
- completed/cancelled mission cannot have scope changed;
- create/update failure does not leave partial MissionAssets/Assignments.

## 16. Non-Goals / Do Not Assume

Do not automatically add these unless already required elsewhere in the project:

- autonomous UAV route planning;
- automatic flight control;
- drone assignment if the current domain does not support it;
- a new GIS provider;
- a second authentication system;
- hard-coded role names when existing permission policies can express the rule;
- automatic mission creation immediately after drawing a polygon;
- recomputing historical mission scope solely from current GIS geometry.

The associated AI research focuses on post-flight RGB UAV imagery/video and explicitly does not attempt to solve autonomous UAV navigation or flight control. This mission-management flow therefore defines inspection scope and assignments, not autonomous flight planning.

---

## 17. Definition of Done

The Mission Management backend is functionally correct when:

- an authorized manager can create a mission only inside their assigned management scope;
- GIS selection can resolve candidate towers without leaking unauthorized assets;
- the final confirmed tower list is persisted as mission scope;
- eligible inspectors can be assigned;
- inspectors can see only assigned missions and their mission-scoped assets;
- backend authorization remains correct even when clients forge IDs or bypass frontend restrictions;
- mission state rules and validation are enforced;
- critical changes are auditable;
- persistence is consistent and duplicate relations are prevented;
- automated tests cover the main authorization and scope boundaries.
